# Agenomics Validation Protocol v1

**Agenomics** · Автор: Dm.Andreyanov · Бренд: Prizolov Lab · 2026

Как проверяется, предсказывает ли Trust Score реальные исходы, и какие
утверждения допустимы на каком объёме данных. Протокол описывает то, что
уже делает код (`agenomics/validation.py`, `agenomics validate`,
`examples/framework_evaluation/`), и фиксирует пороги, ниже которых
заявлений о предсказательной силе не делается.

## 1. Цепочка

```
Наблюдение (прогон агента)
  → Trust Score, посчитанный ДО прогона только из прошлых прогонов
  → Предсказание: score замораживается (frozen_at) под конкретную цель
  → Выполнение агента
  → Донор фиксирует исход ПОСЛЕ заморозки (observed_at > frozen_at)
  → Доказательство с уровнем качества Q0–Q4
  → Пара (предсказание, исход) по одной цели
  → Проверка: holdout по времени, baseline, bootstrap по агентам
```

Score не может зависеть от исхода того же прогона: это проверяется при
записи (`record_outcome` отклоняет исход не позже заморозки) и повторно
при проверке (исходы раньше заморозки отбрасываются и считаются в
отчёте).

С v0.9.6 вместе со score замораживается снимок конфигурации (версии
модели доверия, генома, модели, промпта, фреймворка, задача, окружение)
с SHA-256; `verify_prediction_integrity()` его пересчитывает. Записи
графа неизменяемы: изменение и удаление запрещены триггерами базы,
повтор той же записи не увеличивает N (AEP-001, раздел 7.6).

## 2. Цели

Каждая цель проверяется отдельно, смешивать их нельзя: одна оценка
записана под каждую цель одного прогона.

| Цель | Исход | Донор | Уровень |
|---|---|---|---|
| `runtime_failure` | `execution_error` | runtime monitor | Q1 |
| `security_incident` | `secret_leak` | secret scanner | Q2 |
| `task_failure` | `task_failure` | task checker (`check()` шаблона) | Q3 |
| `incident_in_run` | устаревшая, до v0.9.2 | | |

`task_failure` включает и неверный ответ, и падение прогона не из-за
окружения: задача не выполнена в обоих случаях. При разборе событий
стоит смотреть, какие из них ответы, а какие падения.

У каждого исхода с v0.9.6 есть класс (`TASK`, `SECURITY`, `RUNTIME`,
`BEHAVIORAL`, `INFRASTRUCTURE`) и уровень качества. Фильтр
`agenomics validate --min-quality Q3` оставляет только исходы не ниже
заданного уровня.

## 3. Исключения

- **`infrastructure_error`** (нет ключа, не ставится библиотека, rate
  limit, внешний баг): предсказание исключается целиком, по всем целям.
  Агент не работал, и «утечки не было» у непрогнанного агента ничего не
  значит. `task_outcome` у такого прогона пуст.
- **`check_error`** (результат не той формы, которую ожидает проверка):
  исход задачи неизвестен, пара по `task_failure` не создаётся.
- **Исход раньше заморозки**: отбрасывается.

## 4. Единицы анализа

Отчёт показывает уровни раздельно, и ни один не подменяет другой:

| Уровень | Что это | Где в отчёте |
|---|---|---|
| Предсказание | пара «прогон × цель» | шапка: «предсказаний» |
| Наблюдение | один прогон агента | шапка: «наблюдений (прогонов)»; внутри цели пар столько же, сколько прогонов |
| Агент | фреймворк/агент (`agent_id`) | шапка и каждая цель: «агентов» |
| Конфигурация | `genome_hash`: фреймворк и версия, модель, промпт, домен, автономность | каждая цель: «конфигураций» |
| Донор и группа независимости | кто сообщил исход | каждая цель: «Независимость» |

Повторные прогоны одного агента зависимы. Поэтому доверительные
интервалы считаются bootstrap по агентам (кластерами), а не по парам.

## 5. Процедура

1. Пары одной цели сортируются по времени заморозки.
2. Первые 60% (калибровка) используются только для порога риска и
   baseline; проверка идёт на поздних 40%.
3. Метрики на проверочной части: ROC-AUC с 95% CI (bootstrap по агентам),
   PR-AUC, Brier, ECE; вероятность наивная, p = (100 − score) / 100.
4. Baseline: константа, majority class и **историческая частота событий
   агента**. Последний — главный: он отвечает на вопрос, добавляет ли
   score что-то сверх того, какой это агент.
5. Вердикт:
   - `insufficient_data`: в проверочной части меньше 30 пар или меньше 5
     событий любого класса;
   - `no_evidence_of_signal`: CI ROC-AUC включает 0.5;
   - `signal_not_better_than_baseline`: CI разницы AUC с историей агента
     включает 0;
   - `signal_beats_baseline`: CI разницы выше 0.

Когорты разных версий модели доверия проверяются отдельно:
`agenomics validate <db> --trust-model-version 0.9.5`.

Интервал AUC считается дважды: bootstrap по агентам и по конфигурациям
(`genome_hash`). Сто прогонов одной конфигурации не сто независимых
доказательств, и второй интервал это показывает.

Полный отчёт: `agenomics validate <db> --trust-model-version X --report
validation_report.md` (когорта, объём, доказательства, целостность,
цели). В Framework Evaluation он сохраняется в артефакт каждого прогона.

## 6. Пороги для утверждений

| Уровень данных | Условие (для одной цели) | Допустимая формулировка |
|---|---|---|
| Разведка | меньше 5 событий в проверочной части | «данных для вывода нет»; числа AUC не приводятся как результат |
| Диагностический сигнал | 5–19 событий, вердикт не `insufficient_data` | «в небольшой проспективной когорте наблюдается сигнал, требующий повторения» |
| Предварительный результат | не меньше 20–30 событий на цель, не меньше 20 агентов, `signal_beats_baseline`, повторение на следующей когорте | «на данных X (N прогонов, M агентов) score предсказывает цель лучше истории агента» |
| Внешняя валидность | то же, плюс исходы Q4 (реальные последствия) или подтверждённые человеком, доноры из разных групп независимости | только после этого: «Trust Score предсказывает сбои агентов» |

С v0.9.6 уровень считается автоматически и печатается у каждой цели
(«Уровень утверждений»), вместе со списком того, что мешает следующему
уровню. Пороги: `PROTOCOL_THRESHOLDS` в `agenomics/validation.py`,
единственный источник чисел этого раздела. `preliminary` требует
вердикта `signal_beats_baseline` и на выбранной когорте, и на
предыдущей (`--trust-model-version`); `external` — хотя бы одного
исхода Q4 или подтверждённого человеком. Вердикт при этом остаётся
статистическим ответом и не заменяет уровень.

Не допускаются, пока не достигнут соответствующий уровень:

- «Agenomics предсказывает сбои AI-агентов»;
- ROC-AUC как маркетинговое число без N, числа событий и CI;
- объединение целей или версий в одну выборку ради большего N.

## 7. Внешнее подтверждение (Q4)

Q4 — исход, который наступил в реальном мире и зафиксирован внешней
системой. Внутренние проверки (`check()` шаблона, LLM-судья) это Q3.
Q4 записывается только через `record_external_outcome()`
(`agenomics/external.py`):

- верификатор получает предсказание без Trust Score;
- подтверждение строго позже заморозки;
- группа независимости верификатора не совпадает с группами доноров,
  уже давших исходы этому предсказанию;
- обязательна ссылка на запись во внешней системе.

Первый источник Q4 — `prizolov-sports-ai`: прогноз 1X2 замораживается
до начала матча и подтверждается итоговым счётом из The Odds API. Он
пишет в собственную базу (`/data/agenomics_evidence.db` сервиса), а не в
базу Framework Evaluation. Это отдельная когорта (`external`) с другим
агентом и окружением, и в базе Framework Evaluation Q4 остаётся 0. Пока
Q4 нет, отчёт показывает это как блокер уровня `external`.

## 8. Накопление

`agenomics scorecard <db> --trust-model-version X` показывает, сколько
данных собрано и сколько не хватает до ориентиров
(`ACCUMULATION_TARGETS`: 500 прогонов, 30 агентов, 100 конфигураций,
4 группы независимости, 300 доказательств Q3, 50 Q4, 25 событий на
цель). Это ориентиры накопления, не требования статистической мощности.
Scorecard строится по одной когорте (раздел 10); `--cohort-type all`
печатает по scorecard на каждую.

## 9. Текущее состояние (октябрь 2026)

Разведочный уровень. Эталон: [`docs/baselines/v0.9.3.md`](baselines/v0.9.3.md).
Событий на цель единицы, Q4 и подтверждённых исходов нет. На обычных
прогонах `runtime_failure` и `security_incident` почти не случаются, а
`task_failure` около 3.5%. Поэтому сбор данных изменён (раздел 10):
ротация моделей и задач в natural, стресс-когорты и вторые доноры
([`specs/validation-data-acquisition-v1.md`](specs/validation-data-acquisition-v1.md)).

## 10. Когорты и стресс

У каждого предсказания есть тип когорты (`cohort_type`, в снимке):

| Когорта | Что это |
|---|---|
| `natural` | обычные задачи; модель и задача меняются по номеру запуска |
| `stress_runtime` | перед моделью один раз внедряется сбой провайдера (503, 429, битый JSON) |
| `stress_security` | в найденном документе канарейка и prompt injection |
| `stress_task` | ловушки: отвлекающий ответ, противоречивая инструкция, многошаговость |
| `external` | исходы Q4 внешней системы (sports-ai) |

Правила:

- **Когорты не смешиваются.** `validate` и `scorecard` по умолчанию берут
  `natural`, другие когорты выбираются через `--cohort-type`. Смесь
  (`all`) печатается с предупреждением, и вывод на ней не делается.
- **Одно условие для всех агентов** в каждом запуске. Иначе частота
  событий отражала бы то, кому какой стресс достался, а не агента.
- **Внедрённая поломка не исход.** Исходом считается только реакция
  агента: упал на внедрённом сбое, раскрыл канарейку, ответил неверно.
  Если настоящий провайдер сам ответил ошибкой, это сбой окружения, и
  прогон исключается.
- **История для Trust Score только из `natural`.** Стресс-условия задаём
  мы, и score не должен от них зависеть. Стресс-когорты проверяют, как
  существующий score предсказывает поведение под стрессом.
- **Вторые доноры** должны иметь другой механизм ошибки. У `task_failure`
  это LLM-судья на другой модели (`llm_judge`): он видит только задачу и
  ответ. Отчёт показывает согласие судьи и проверки. У `security_incident`
  в `stress_security` это точное совпадение канарейки
  (`canary_exact_match`). Оно и regex-сканер смотрят на разные события,
  поэтому согласие для security не считается. **У `runtime_failure`
  второго донора нет**: код выхода процесса выводится из того же
  исключения и независимости не даёт.
- **Сценарий, который ничего не различает, заменяется.** Если после 50
  прогонов частота событий выходит за 5–95% по всем агентам сразу,
  сценарий выводится из ротации. Решение принимается только по общей
  частоте, не по связи со score, и записывается в журнал ТЗ.

## 11. Что показывает отчёт и как читать смену условий

- **Объём выборки отчёта** считается по тем же когорте, версии модели
  доверия и периоду, что и вердикты: прогоны, исключённые прогоны по классу
  ошибки (`model_unavailable`, `rate_limit`, `harness_error` и т. п.),
  агенты, конфигурации, доказательства и исходы по качеству. Вся база идёт
  отдельным разделом, только для контекста.
- **Смена условий.** Holdout делится по времени. Если условия сбора
  поменялись (Framework Evaluation с запуска 119: ротация моделей и задач;
  с запуска 126 только доступные модели), калибровочная и проверочная части
  относятся к разным условиям, и AUC на holdout отвечает не на тот вопрос.
  Такой период проверяется отдельно: `agenomics validate --since <дата>`.
  В артефакте прогона это `validation_report_natural_current.md`.
- **По условиям и моделям.** У каждой цели таблица пар и событий по условию
  (`task_version`) и по модели. Для цели, ради которой устроена
  стресс-когорта, там же статус правила раздела 10 по каждому сценарию:
  «рано» (меньше 50 прогонов), «различает» или «заменить».
- **Q4** показывается отдельным разделом. В базе Framework Evaluation он
  0 по устройству; проверка Q4 идёт по базе prizolov-sports-ai
  (`GET /api/v1/admin/agenomics` сервиса).
- Зелёный job означает, что прогон и отчёты отработали, а не что сигнал
  подтверждён: вердикт и уровень утверждений смотрятся в отчёте.
