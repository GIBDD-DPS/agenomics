# AEP-001: Agenomics Evidence Protocol v1.0

**Автор**: Dm.Andreyanov · **Проект**: Prizolov Lab
**Статус**: реализовано в коде, `agenomics/evidence.py`, `agenomics/feedback.py` (v0.7.1; поля Observation дополнены в v0.7.2 и v0.7.11, см. раздел 1)

## Зачем отдельный протокол, а не просто "поля в базе"

`EvidenceStore` появился в v0.7.0 как персистентное хранилище. Но
персистентность одного человека, это ещё не протокол: если два разных
пользователя Agenomics начнут собирать данные каждый по-своему (разные
поля, разные единицы измерения периода, разный смысл "severity"), их
данные будет невозможно объединить в один датасет. AEP-001 фиксирует
схему, чтобы данные из разных источников были сравнимы и агрегируемы,
это предпосылка для содержательного `Incident Correlation` на масштабе
"47 агентов из 12 доменов", а не "мои 20 наблюдений".

## 1. Observation

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| `agent_id` | str | да | Идентификатор агента |
| `timestamp` | ISO 8601 datetime | да | Момент оценки |
| `declared_score` | float [0,100] | да | Trust Score на момент оценки |
| `declared_label` | str | да | Trusted/Conditional/High Risk |
| `declared_confidence` | str | нет | High/Medium/Low (см. `TrustResult.confidence`) |
| `genome_hash` | str | нет | Хэш генома на момент оценки (см. `GenomeLedger`) |
| `genome_version` | str | нет | Версия/итерация генома, если ведёте версионирование вручную |
| `trust_model_version` | str | нет | Версия `agenomics`, которой считался score |
| `evaluation_period` | str | нет | Период, за который агрегировано наблюдение (например, диапазон дат) |
| `request_count` | int | нет | Сколько запросов/обращений обработано за период |
| `schema_version` | str | нет (проставляется автоматически) | Версия AEP, по которой записано наблюдение |
| `collector` | str | нет | Кто/что собрало данные (`"sdk"`, `"manual"`, `"import"`) |
| `source` | str | нет | Источник/окружение (например, имя кластера или деплоя) |
| `execution_status` | str: `"success"`/`"error"` | нет | Чем закончился прогон агента, к которому относится наблюдение (с v0.7.2) |
| `duration_seconds` | float | нет | Длительность этого прогона в секундах (с v0.7.2) |
| `model_version` | str | нет | Провайдер и модель, которую вызывал агент, например `"groq/openai/gpt-oss-20b"` (с v0.7.11) |
| `prompt_version` | str | нет | Версия системного промпта агента, в любом формате, который вы ведёте сами (с v0.7.11) |
| `framework_version` | str | нет | Версия библиотеки агентного фреймворка, например `"crewai==0.1.0"` (с v0.8.0) |
| `observed_model_version` | str | нет | Модель, которую реально вернул провайдер в ответе, в отличие от заявленной `model_version` (с v0.8.0) |
| `task_outcome` | str: `"success"`/`"failure"`/`"partial"` | нет | Исход задачи, а не факт выполнения; `null` значит исход неизвестен. Дописывается после задачи через `record_task_outcome()`, один раз (с v0.8.0) |

Реализация: `agenomics.evidence.EvidenceStore.record_observation()`.

`execution_status` и `duration_seconds` появились в коде в v0.7.2, но в
этот документ не были внесены до v0.7.11. Всё это время они
записывались и использовались (`examples/framework_evaluation/` строит
по ним `predictability`), так что данные, собранные с v0.7.2, их уже
содержат. Изменилась только документация, не схема.

`model_version`/`prompt_version` описывают агента, `trust_model_version`
описывает agenomics. Это разные вопросы: без первых двух смена модели
или промпта выглядит в истории как дрейф самого агента. В отличие от
`trust_model_version`, они не проставляются автоматически: agenomics не
знает, какую модель вызывал агент, и `None` честнее угаданного значения.

`framework_version` (с v0.8.0) нужен по той же причине, что и
`model_version`: обновление библиотеки фреймворка без него выглядит в
истории как дрейф агента. `observed_model_version` отличается от
`model_version` источником: первое взято из ответа провайдера, второе
заявлено вызывающим кодом. Расхождение значит, что отработала не та
модель, которая заявлена.

Все эти поля опциональны и не меняют `AEP_SCHEMA_VERSION` (раздел 5):
добавление необязательного поля совместимо с данными, записанными
раньше, у которых эти поля просто `None`. Файл базы, созданный старой
версией, получает недостающие колонки автоматически при открытии.

## 2. Incident

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| `description` | str | да | Короткое служебное резюме, **не сырой пользовательский текст** (см. Privacy) |
| `severity` | enum: minor/moderate/severe | да | Тяжесть инцидента |
| `category` | enum: response_quality/safety/data_leak/bias/hallucination/compliance/infrastructure/other | нет | Структурированная категория, предпочтительнее свободного текста для агрегации |
| `source` | enum: user_report/automated_monitor/manual_review/support_ticket/other | нет | Откуда взят инцидент |
| `confirmed` | bool | нет (по умолчанию `True`) | Подтверждён ли инцидент человеком, а не только авто-флагом |
| `resolution` | str | нет | `"fixed"`/`"false_positive"`/`"pending"` или свободный текст |
| `axis` | str | нет | Какая ось Trust Score, по вашей оценке, связана с инцидентом |

Реализация: `agenomics.Incident`, `agenomics.IncidentCategory`, `agenomics.IncidentSource` (`feedback.py`).

`infrastructure` (с v0.7.12) означает сбой окружения, а не поведения
агента: не установлена зависимость, нет API-ключа, rate limit
провайдера, модель недоступна, баг в самом фреймворке. При
сопоставлении Trust Score с инцидентами такие записи стоит исключать
или анализировать отдельно: они характеризуют инфраструктуру запуска,
а не доверие к агенту. Новое значение enum не меняет
`AEP_SCHEMA_VERSION`: поле по-прежнему опционально, старые данные
валидны.

Все новые поля (`category`, `source`, `confirmed`, `resolution`)
опциональны. Код, написанный до AEP-001 (`Incident(description, severity)`),
продолжает работать без изменений.

## 3. Provenance

Поля `schema_version`, `collector`, `source`, `trust_model_version`,
`model_version`, `prompt_version`, `framework_version`,
`observed_model_version` в Observation (раздел 1) одновременно
выполняют функцию Provenance.
Отдельной таблицы для них не заводили, чтобы не усложнять схему на
этапе, когда реальных данных ещё нет. Если/когда появится необходимость
агрегировать данные из явно разных организаций одновременно, это
кандидат на вынесение в отдельную таблицу в будущей ревизии протокола.

## 4. Privacy: обязательное правило, не рекомендация

**По умолчанию: никаких сырых пользовательских текстов.**

`description` в Incident предназначен для короткого служебного резюме
("жалоба на тон ответа"), а не для копирования реальной переписки
пользователя. Для агрегации и сравнения между источниками данных
используйте `category` (структурированный enum): он агрегируется
корректно, а свободный текст нет.

Начиная с v0.7.1, `Incident.__post_init__()` выдаёт `UserWarning`, если
`description` длиннее 200 символов. Это эвристика, а не строгая
валидация (не хочет блокировать законные случаи чуть более длинного
резюме), но сигнал стоит воспринимать всерьёз.

Если вам нужно связать инцидент с конкретным пользовательским
обращением для внутреннего разбора, храните это связывание в вашей
собственной системе (тикет-трекере), а в Agenomics передавайте только
`category`/`severity`/ссылку на внешний ID, если нужно, а не сам текст.

## 5. Версионирование протокола

`AEP_SCHEMA_VERSION = "1.0"` (`agenomics.evidence.AEP_SCHEMA_VERSION`)
проставляется автоматически в каждое наблюдение. Будущие ревизии
протокола (добавление обязательных полей, изменение семантики) должны
бампать эту константу, чтобы данные, собранные по разным версиям
протокола, можно было отличить при агрегации.

## 6. Что протокол сознательно НЕ включает (пока)

- **ML-калибровка на основе Incident**: протокол описывает, что
  хранить, а не как это использовать для обучения моделей. Это
  сознательно отложено до накопления реального датасета (см.
  `docs/CONNECT_YOUR_AGENTS.md`). Обучать что-либо на 10-20
  наблюдениях было бы фикцией, а не калибровкой.
- **Единый формат обмена между организациями** (JSON Schema/Protobuf):
  на этапе, когда данных ни у кого нет, стандартизировать формат обмена
  преждевременно. `export_json()`/`export_csv()` достаточно для
  текущего масштаба использования.
- **Отдельная таблица Provenance**: см. раздел 3.
