# Framework Evaluation. Автоматический сбор реальных наблюдений для Agenomics

Автоматически прогоняет все обнаруженные фреймворки, строит честный
`AgentGenome` из захваченных логов и записывает реальный `TrustScorer`
результат в персистентный `EvidenceStore` (AEP-001).

## Быстрый старт

```bash
pip install agenomics
```

1. Скопируйте `frameworks/_example_template.py` в `frameworks/ваш_агент.py`
   (без ведущего подчёркивания), замените `run()` на реальный вызов
   и укажите `MODEL_VERSION` (провайдер/модель, которую реально вызывает
   `run()`, например `"groq/openai/gpt-oss-20b"`). Пишется в
   `EvidenceStore.model_version`; `test_pipeline.py` проверяет, что
   значение совпадает с моделью в коде шаблона. Там же `FRAMEWORK_PACKAGE`
   (pip-имя библиотеки, её версия пишется в `framework_version`) и
   `CI_TIER`
2. Запустите: `python run_all_frameworks.py`
3. Повторяйте, история накапливается в `frameworks_evidence.db`

## Required и experimental (v0.8.0)

Каждый шаблон объявляет `CI_TIER`. Падение `required`-фреймворка
завершает `run_all_frameworks.py` с кодом 1, и job в GitHub Actions
становится красным. Падения `experimental` видны в итоговом отчёте, но CI
не валят. Шаблон без `CI_TIER` считается `experimental`: новый фреймворк
сначала должен доказать, что стабильно проходит.

Разделение на 24.09.2026 взято из прогона по расписанию №73: 14
фреймворков, прошедших его, `required`; `atomic_agents`, `crewai`,
`google_adk`, `smolagents`, `txtai` упали и стали `experimental`.
Новые шаблоны v0.9.5 и переведённые на Groq smolagents и Google ADK
начинают как `experimental`.
Когда experimental-фреймворк стабильно проходит, переведите его в
`required` правкой одной строки в шаблоне.

База с историей сохраняется в кэш и артефакт и при красном job
(`if: always()`), иначе история терялась бы ровно в тех запусках, где
что-то сломалось.

В конце отчёта раннер сверяет `MODEL_VERSION` с моделью, которую вернул
провайдер (`observed_model_version`), и перечисляет фреймворки, для
которых модель в результате `run()` найти не удалось: там сверка не
проводится, а не считается пройденной.

## Что уже включено: 19 активных шаблонов, все на Groq

Наличие шаблона не означает гарантированную production-совместимость.
Это отправная точка для сбора реальных наблюдений, не готовая интеграция.
Синтаксис каждого шаблона сверен с актуальной документацией на момент
добавления, но библиотеки быстро меняются.

С v0.9.5 все активные шаблоны работают через **Groq** (бесплатный
уровень, без карты, `console.groq.com/keys`) на одной модели
`openai/gpt-oss-20b`, и нужен только один ключ, `GROQ_API_KEY`.
В GitHub Actions он задаётся как секрет репозитория: Settings → Secrets
and variables → Actions.

**Активные (19):** LangChain, AG2 (AutoGen), LlamaIndex, LangGraph,
Haystack, CAMEL-AI, Griptape, Agno, Pydantic AI, DSPy, Swarms, Semantic
Kernel, OpenAI Agents SDK, BeeAI, smolagents, Google ADK; с v0.9.5 также
Strands Agents (AWS), Deep Agents (LangChain) и Microsoft Agent Framework.

**Выключены (`DISABLED`, v0.9.5):** Atomic Agents (import_error в каждом
прогоне), CrewAI (внешний баг и конфликт pydantic), txtai (rate_limit
почти в каждом прогоне). Файлы и накопленная история остаются, раннер их
не запускает и перечисляет в начале отчёта с причиной. Включить обратно:
удалить строку `DISABLED` в шаблоне и вернуть установку библиотеки в
`framework_eval.yml`.

**Переведены на Groq (v0.9.5):** smolagents (раньше Hugging Face
Inference, нужен был `HF_TOKEN`) и Google ADK (раньше Gemini, нужен был
`GOOGLE_API_KEY`). Этих ключей в CI не было, и все их прогоны уходили в
`infrastructure_error`, не давая данных об агенте. Смена модели видна в
`model_version`.

### Как выбирались замены

Критерии: работает на уже имеющемся ключе Groq; ставится в одно окружение
с остальными, не ломая их; при ошибке провайдера бросает исключение, а не
возвращает пустой или «успешный» результат; возвращает объект, из которого
однозначно берётся итоговый ответ. Каждый новый шаблон проверен на
локальной OpenAI-совместимой заглушке Groq: правильный ответ проходит
`check()`, неверный нет, недоступный провайдер даёт исключение. Весь
набор затем прогнан в окружении, собранном теми же командами, что в
`framework_eval.yml`: все фреймворки стоят в одном окружении, и новый
пакет может сломать соседей.

Проверены и не взяты:

- **Microsoft AutoGen AgentChat**: понижает `protobuf` до 5.29, после
  чего AG2 (required) падает на загрузке Google-модулей; сам AutoGen в
  режиме поддержки, его преемник Microsoft Agent Framework в наборе.

- **Langroid**: требует `mcp` 2.x, с которым не импортируется CAMEL-AI
  (required); кроме того, известная уязвимость PYSEC-2026-2579.
- **PraisonAI Agents**: при ошибке модели печатает её и возвращает `None`
  вместо исключения; сбой провайдера выглядел бы как «исход неизвестен».

Раньше из набора исключались по другим причинам: Rasa, AutoGPT, Letta,
Portia AI, AgentScope (нужен отдельный сервер или облачный аккаунт),
MetaGPT (платный), SuperAGI (неподдерживаем, открытые уязвимости), Marvin.

### Фреймворки, которые скрывают ошибки провайдера

Griptape, Agno и Swarms при ошибке провайдера (нет сети, 401, 429) не
бросают исключение: Griptape кладёт её в `ErrorArtifact`, Agno ставит
`RunStatus.ERROR`, Swarms пишет в лог и возвращает пустую строку. До v0.9.5
такой сбой записывался как неверный ответ агента (`task_failure`). Теперь
их `run()` превращает это в исключение, и прогон классифицируется по
причине (например, `rate_limit`).

## Автоматический запуск по расписанию

`.github/workflows/framework_eval.yml` прогоняет каждые 6 часов через
GitHub Actions. Важно: сам этот файл должен лежать в `.github/workflows/`
в корне репозитория, не внутри `examples/framework_evaluation/`, иначе
GitHub Actions его просто не увидит. Скрипты и БД при этом остаются в
`examples/framework_evaluation/`, это решается через `working-directory`
в самом workflow.

**Про кэш БД между запусками (`actions/cache`):**
- Кэш GitHub Actions иммутабелен: записанный под конкретным ключом кэш
  нельзя перезаписать в конце того же запуска. Поэтому используется
  уникальный ключ на каждый запуск (`github.run_id`) плюс `restore-keys`
  по префиксу, чтобы находить самый свежий предыдущий кэш при
  восстановлении.
- GitHub удаляет неиспользуемые кэши через 7 дней и держит лимит 10GB
  на репозиторий. При расписании раз в 6 часов это не проблема, кэш
  обновляется чаще, чем истекает. Если смените cron на реже раза в
  неделю, переключитесь на настоящую БД (Postgres/S3) вместо кэша.

Загрузите этот репозиторий (или папку) на GitHub, включите Actions,
дальше расписание работает само, без ручного запуска.

## Структура

- `capture_log_v2.py`: безопасный захват логов (падение одного
  фреймворка не мешает остальным)
- `genome_from_capture.py`: честное построение генома. `data_safety`
  через реальный детектор утечек секретов, `predictability` из истории
  3+ прогонов (реконструируется из `EvidenceStore`, переживает
  перезапуск процесса), `bias_control`/`transparency` осознанно `None`,
  их нельзя вывести из лога выполнения, `has_ledger` по умолчанию
  `False`, захват лога инструментом не делает агента обладателем
  собственного журнала решений
- `full_pipeline.py`: склеивает всё в один вызов
  `run_framework_and_record()`. С v0.7.12 score считается **до**
  прогона, только из прошлых прогонов (`derive_genome_pre_run()`):
  статус, длительность и утечки текущего прогона пишутся в наблюдение
  как исход, но не влияют на его score. Ошибка классифицируется при
  записи: сбои окружения (ImportError, нет ключа, rate limit, модель
  недоступна) получают категорию `infrastructure`, остальные `other`,
  точный класс стоит префиксом в описании (`[import_error] ...`)
- `run_all_frameworks.py`: авто-обнаружение плагинов в `frameworks/`
- `test_pipeline.py`: тесты на всё вышеперечисленное, включая отсутствие target leakage
- `classify_failures.py`: классифицирует причины падения по уже сохранённому тексту инцидента (rate limit / import error / устаревшая модель / auth и т.д.), без изменения схемы. Наблюдения до v0.7.4 честно попадают в "other", детали для классификации в них не сохранялись

## Evidence Graph (v0.9.0)

Каждый прогон пишет в `EvidenceStore` не только наблюдение, но и граф
доказательств (AEP-001, раздел 7):

1. **до запуска**: наблюдение с Trust Score, посчитанным по прошлым
   прогонам, и отдельное предсказание на каждую цель (v0.9.2):
   `runtime_failure`, `security_incident` и, если в шаблоне есть
   `check()`, `task_failure`. Оценка у них одна, проверяются они порознь;
2. **после**: статус выполнения, доказательства и исходы от независимых
   доноров:

   | Донор | Группа | Качество | Исход для цели |
   |---|---|---|---|
   | `framework_eval.runtime_monitor` | `runtime` | Q1 | `runtime_failure`: `execution_error` |
   | `framework_eval.secret_scanner.v1` | `regex_secret_scanner` | Q2 | `security_incident`: `secret_leak` |
   | `framework_eval.task_checker` | `task_checker` | Q3 | `task_failure`: ответ агента не прошёл `check()` |

   Если прогон упал из-за окружения, **каждое** его предсказание получает
   `infrastructure_error` и исключается из проверки целиком: агент не
   работал, и «утечки не было» у непрогнанного агента ничего не значит.

`check(result)` есть у всех шаблонов (с v0.9.4). У `smolagents`
задача: сумма 1..10 = 55; у `dspy`, `llamaindex`, `langchain`: погода
из инструмента; у остальных 15: арифметическая задача в одно действие
или два с просьбой «Ответь одним числом» (у каждого шаблона своя, ответ
не встречается в условии). Проверяется **итоговый ответ агента**, а не
весь результат: в LangChain вывод инструмента «It's always sunny» лежит
в истории сообщений, и проверка по нему прошла бы при любом ответе.
Разряды нормализуются («1 800» и «1,800» это 1800).

Если результат не той формы, которую ждёт `check()` (фреймворк сменил
API), проверка бросает исключение и исход записывается как неизвестный
(`check_error`), а не как провал агента. Пустой ответ агента это провал.

Смена задачи меняет конфигурацию агента: у 15 шаблонов объявлен
`PROMPT_VERSION = "task-v2"`, поэтому `genome_hash` новый, и история
прогонов с открытыми вопросами не смешивается с новой.

`task_outcome` описывает только задачу: упал прогон, значит `failure`;
есть `check()`, значит её результат; иначе пусто. Утечка секрета это
`security_incident`, а не провал задачи (до v0.9.2 было иначе).

Прерванный прогон оставляет предсказание без исхода, а не собранную
задним числом запись.

`genome_hash` здесь описывает конфигурацию агента (фреймворк и его
версия, модель, промпт, домен, автономность), а не состояние, выведенное
из истории: до v0.9.0 он менялся почти каждый прогон, и 19 агентов
выглядели как сотни «уникальных геномов».

Падения из-за окружения (`infrastructure_error`: ImportError, нет ключа,
rate limit) не снижают `predictability` в Trust Score и считаются
отдельно, как надёжность запуска (`reliability` в выводе раннера).
Тяжесть инцидента зависит от класса ошибки: rate limit `minor`, сбои
окружения `moderate`, нераспознанная ошибка и утечка секрета `severe`.

## Честная граница

**Данные до v0.7.12 не годятся для проверки связи score с инцидентами.**
До v0.7.12 score наблюдения считался по логу и статусу того же прогона,
что и его инциденты: упавший прогон одновременно снижал predictability
и давал инцидент, найденная утечка одновременно снижала data_safety и
давала инцидент `data_leak`. Корреляция на таких данных возникает по
построению. Новые наблюдения помечены `source="full_pipeline.py/pre-run"`,
старые имеют `source="full_pipeline.py"`. Для анализа берите только
первые, для истории статусов (predictability) годятся и те, и другие.
Инциденты категории `infrastructure` характеризуют CI и зависимости,
а не агента, их стоит исключать или анализировать отдельно.

`declared_score` в каждом наблюдении: это настоящий
`TrustScorer.score()`, а не заглушка, но построенный на частичном
геноме (2 из 5 осей выводятся автоматически, 2 остаются
недостаточными для оценки). Confidence в отчёте будет честно
невысоким, пока вы не дополните `bias_control`/`transparency` вручную
(например, через промпт Trust Auditor) для каждого фреймворка отдельно.
